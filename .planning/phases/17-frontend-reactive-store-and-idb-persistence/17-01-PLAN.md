**1. Add `normalizeTokens` helper at module scope** (near `hydrateTrace`, before the class definition):

```js
function normalizeTokens(t) {
    if (!t) return { input: 0, output: 0, cache_read: 0, cache_write: 0, reasoning: 0, total: 0 };
    return {
        input: t.input ?? 0,
        output: t.output ?? 0,
        cache_read: t.cached ?? 0,   // backend 'cached' -> store 'cache_read'
        cache_write: t.cache_write ?? 0,
        reasoning: t.reasoning ?? 0,
        total: t.total ?? 0,
    };
}
```

Key mapping: backend emits `tokens.cached` (single field) but store schema uses `cache_read` per CONTEXT.md locked decision. `cache_write` always 0 (no backend field exists yet). Add a comment documenting this translation.

**2. Extend `_onIteration` handler** — add three fields to the object literal inside `trace.iterations.set()`:

```js
// Phase 17: token/timing/provider fields
tokens: normalizeTokens(payload.tokens),
duration_ms: payload.duration_ms ?? 0,
ai_provider: payload.provider ?? null,
```

Place these INSIDE the initial `iterations.set()` object literal (after the `error` field), NOT as a separate post-creation mutation. This follows the research recommendation to avoid the pitfall of setting fields after creation. The existing guard `if (!trace.iterations.has(...))` means this code runs exactly once per iteration.

**3. Add `getTraceTotals(trace)` method** on AiDebugApp class — place it in the "Iteration duration helpers" section (after `_formatDuration`):

```js
getTraceTotals(trace) {
    let total_tokens = 0, total_duration_ms = 0,
        total_input = 0, total_output = 0,
        total_cached = 0, total_reasoning = 0;
    for (const iter of trace.iterations.values()) {
        const t = iter.tokens;
        if (t) {
            total_input += t.input || 0;
            total_output += t.output || 0;
            total_cached += t.cache_read || 0;
            total_reasoning += t.reasoning || 0;
            total_tokens += t.total || 0;
        }
        total_duration_ms += iter.duration_ms || 0;
    }
    return { total_tokens, total_duration_ms, total_input, total_output, total_cached, total_reasoning };
}
```

This method is reactive when called from OWL templates — iterating `trace.iterations.values()` and reading `.tokens`/`.duration_ms` through reactive proxies triggers re-render when any iteration's token data changes. This is what makes SIDE-02 work: Phase 18 templates reading `getTraceTotals(trace).total_tokens` will re-render as each new iteration event arrives.

**Important constraints:**
- Do NOT add a `hasTokenData` flag (locked decision: use `iter.has_error` for distinguishing errored iterations)
- Do NOT add any per-event IDB writes — persist fires only on `loop_end` (existing pattern in `_onLoopEnd`)
- Do NOT maintain an incremental accumulator on the trace object — compute on access via `getTraceTotals()`
- Store exposes raw numbers only — no formatting (locked decision: formatting is Phase 18's concern)
