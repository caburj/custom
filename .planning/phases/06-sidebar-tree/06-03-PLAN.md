  <name>Task 1: Replace reactive(new Map()) with useState(new Map()) for trace store</name>
  <files>ai_debug/static/src/app/app.js</files>
  <action>
In `ai_debug/static/src/app/app.js`, line 15 in `setup()`:

Change:
```js
this.traces = reactive(new Map());
```

To:
```js
this.traces = useState(new Map());
```

Update the comment on line 13 to reflect the change:
```js
// Trace data store — useState wraps the Map so OWL's render function
// observes mutations (.set/.delete/.clear) and triggers re-renders.
// Nested reactive Maps (iterations, toolCalls) inherit the render
// callback when accessed through this proxy chain.
```

Root cause (from debug session): `reactive(target)` without a second argument uses `NO_CALLBACK` sentinel. OWL's `observeTargetKey()` returns early when `callback === NO_CALLBACK`, so no component render is ever registered as observer. `useState(state)` calls `reactive(state, render)` internally, passing the component's batched render function as callback.

The nested `reactive(new Map())` calls inside `_onNewTrace` (line 48, for iterations) and `_onIteration` (line 71, for toolCalls) do NOT need to change. When accessed through the `useState`-wrapped parent Map, OWL's `possiblyReactive()` wraps them with the same render callback. The explicit `reactive()` wrapping is harmless — it adds a proxy layer, but accessing through the parent provides the callback.

Do NOT change any other code. The bus handlers, selection methods, ancestor getters, duration helpers, and all other logic remain exactly as-is.

Note: This reverses the [06-01] decision "reactive(new Map()) for trace store — NOT inside useState". The debug session proved that decision was based on incorrect understanding of OWL's reactive observation model.
